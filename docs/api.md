# Dono REST API contract

Status: **proposed contract, not implemented**. All business endpoints belong to a **Python FastAPI backend** under `backend/app/api/`, grouped with APIRouter and mounted at `/api/v1`. Next.js provides the frontend. This follows the user's revised stack choice; no application or migrations have been created. [FastAPI application structure](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

[AGENTS.md](../AGENTS.md) is authoritative. The [database design](databases.md), [requirements](requirements.md), [use cases](features.md) and [architecture](architecture.md) define scope and ownership. [The ERD](architecture/database-erd.html) shows the same proposed entities. The version prefix and DTOs below are technical design proposals; DB-P01–DB-P07 in databases.md explicitly preserve unresolved business choices. No migrations, route files, authentication provider integration or backend implementation are generated by this specification.

Company donations remain in MVP scope under the same authenticated donor ownership. A donation records donor_kind and a company_name snapshot when applicable. There are no company teams, admin roles, or verification workflows. Both donor kinds follow the same unopened, ambient, non-perishable food rules. Chilled/frozen donations and tax receipts are deferred.

## HTTP, authentication and permissions

**Current frontend boundary:** the [2026-10-25 demo decisions](requirements.md#current-frontend-decisions--2026-10-25) include staff refusal at reception and explicit unmatched-offer posting for association browsing. This contract defines neither operation nor its local record. The frontend keeps these records in browser-local state without adding an endpoint or changing the DTOs below. Its multiple-photo preview limit is also local, pending the production upload policy.

Base path: `/api/v1`. FastAPI routers group account, associations, donations, bookings and inventory operations; dependencies verify identity, and Python services own business rules and transaction orchestration through persistence/provider ports. Routers validate Pydantic request models and serialize explicit response models; no ORM or framework objects cross the domain boundary. Next.js renders the views and calls this API, without duplicating business endpoints or provider calls in Route Handlers/server actions. All product endpoints require a verified Supabase subject and application profile. Sign-in/bootstrap remains AMB-002, delegated to Supabase Auth; no bespoke password service or outbound email flow is specified.

The API accepts `Authorization: Bearer <Supabase access token>`. FastAPI verifies signature, approved algorithm, issuer, audience and validity using the selected project's supported verification path; merely decoding a JWT is insufficient. Use the project's published signing keys for asymmetric tokens or the documented Auth verification path for legacy signing; do not expose JWT signing secrets to Next.js. Read current protected role/membership records for permissions. Never treat an API key, client role header or editable user_metadata as user authorization. [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts)

Production may route `/api/v1` to FastAPI behind the same public origin; local development can use a separate backend origin. Configure an explicit frontend-origin allowlist and allow the required Authorization, Content-Type and Idempotency-Key headers plus supported methods/preflight. Never use wildcard credentials/origins. CORS is a browser control, not authorization. The business API does not implicitly authenticate requests from frontend cookies; any later cookie-authenticated API mode requires an explicit CSRF/session design. Supabase session establishment/refresh in the frontend remains separate from the bearer contract. [FastAPI CORS](https://fastapi.tiangolo.com/tutorial/cors/)

Permission symbols used in the endpoint tables:

| Code | Meaning |
|---|---|
| U | Any authenticated application account, acting on permitted shared data or its own profile. |
| D | Donation's verified owner; read scope alone does not grant decision rights. |
| M | Active `assoc_admin` or `assoc_staff` membership in the **target association**. |
| A | Active `assoc_admin` for the association; configuration restriction is provisional DB-P01 / AMB-001. |
| P | Protected `platform_admin` capability, for association approval only. |
| R | Parent donation readable by D or M, with scoped FK agreement; no platform-wide donation read. |

Every resource access is reauthorized, including retries, photo content, QR and derived metrics. Foreign/private resource IDs return 404 without existence disclosure. A known capability failure such as a non-platform user calling a platform-only collection returns 403. Actors, donor IDs, association membership and provenance are derived server-side. Ordinary reads use user-scoped RLS. The narrowly privileged matching, upload/analysis persistence and signed-QR operations follow the server capability boundaries in databases.md; a service-role credential is not a product permission.

JSON requests use `Content-Type: application/json`; upload uses multipart. Responses are private and `Cache-Control: no-store`, including status, metrics, photos and QR. Do not log QR payloads, tokens, raw photos or donor addresses. Server-only provider/service/QR signing keys never appear in JSON, client modules or public environment variables. Public metadata and internal DB objects have separate explicit grants and RLS. [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api)

## Shared wire conventions

The compact TypeScript notation below describes JSON wire DTOs for the Next.js client, not a TypeScript backend. FastAPI will implement matching Pydantic request/response models and Python string enums, with extra fields forbidden and explicit decimal/bigint string serialization. Objects are **closed**: undeclared body/query fields are validation errors, including `donor_id`, raw `status`, `provider`, `model`, `confidence`, `indicators` and `decided_by` in donor write payloads. Optional means omittable; `| null` explicitly permits NULL. All dates/times are validated, not merely regex-matched.

```ts
type UUID = string;       // Canonical UUID text; URL IDs use the same type.
type Instant = string;    // RFC 3339 timestamp with timezone; responses use UTC Z.
type DateOnly = string;   // Valid YYYY-MM-DD source calendar date.
type Revision = string;   // Positive bigint decimal string; never a JSON float.
type Quantity = string;   // Exact numeric(12,3) decimal string, at most 9 whole + 3 fractional digits.
type DonorKind = "individual" | "company";
type Category = "clothes" | "shoes" | "food" | "para" | "furniture";
type Status = "draft" | "offered" | "approved" | "refused" | "booked" | "received" | "distributed";
type Decision = "approved" | "refused";
type Level = "low" | "medium" | "high";
type Unit = "item"; // Initial DB-P03 quantity_unit proposal; extension requires AMB-008.
type Season = "spring" | "summer" | "autumn" | "winter"; // Proposed need_season labels; AMB-009 remains open.
type Attributes = Record<string, unknown>; // Closed per chosen category schema, never arbitrary executable content.
type Single<T> = { data: T; meta: { request_id: UUID; idempotent_replay?: boolean } };
type Page<T> = {
  data: T[];
  page: { next_cursor: string | null; has_more: boolean };
  meta: { request_id: UUID; as_of?: Instant; reference_date?: DateOnly | null; policy_version?: string | null };
};
type ErrorResponse = {
  error: { code: string; message: string; request_id: UUID; retryable: boolean;
           details?: { path: string; code: string }[]; ambiguity_ids?: string[] };
};
```

Donation/need/movement input quantities are positive. Configured capacity and computed read quantities are nonnegative and may be zero, including available capacity/demand, remaining stock and totals. The shared Quantity wire type describes decimal precision, not a blanket positive-only rule. Unit strings must belong to the agreed category policy and match across donation/need/capacity; `item` requires an integral quantity. The Unit and Season labels mirror the named PostgreSQL enums; their provisional vocabularies do not settle quantity/season policy. No model-derived arithmetic or implicit unit conversion. Probabilities/confidence in read-only AI DTOs are numbers in the proposed finite [0,1] contract; preserve original values without fixed-scale rounding. Human percentage formatting is display code.

Mutating existing configuration/donation resources requires `expected_revision` in the body. Missing/invalid versions are 422; a different current version is 409 `stale_revision`. Revisions protect stored facts/configuration, not the freshness of computed capacity, date views or matching results. There is no stable HTTP ETag claim for time-varying expiry output.

All persisted POST/PATCH/PUT commands require `Idempotency-Key: <UUID>`. Hash method, canonical resource path, validated payload (including expected_revision) and relevant validated file digest. Same actor/key/operation/body returns the original success status and resource/event identity after reauthorization, without repeating the effect; a different body returns 409. Check a completed matching replay before rejecting the repeated request's old expected_revision. In-progress external work returns 409 `request_in_progress` with configured retry guidance; only the current lease attempt may finalize. Error responses are not claimed as successful resource creation. The ledger is `private.api_requests`, not an in-memory serverless cache. Store only stable resource/event references and historical action outcomes in result_refs; rebuild current mutable DTOs and read-time expiry/balance/count/mismatch values on replay. A replay is not a byte-identical historical response snapshot. QR payloads, derived expiry values, private URLs and credentials are never cached there. Replay retention/lease settings remain AMB-015/019.

Reads and read-like POST matching/QR resolution/needs parsing do not require retry keys because they persist no product state. AI analysis can be synchronous for this MVP: success returns 201 only after evidence commits; timeout/provider failure returns an explicit error rather than a fake queued/success resource. No worker queue or asynchronous status service is added. External provider billing is not guaranteed exactly once.

## Read schemas

Database snake_case is retained in DTOs for traceability. Read-only server fields cannot be accepted through a generic patch. Resource schemas describe their listed fields, not raw unrestricted table serialization.

```ts
type Profile = { id: UUID; display_name: string | null; platform_role: "donor" | "platform_admin";
                 revision: Revision; created_at: Instant; updated_at: Instant };
type Membership = { association_id: UUID; profile_id: UUID; role: "assoc_admin" | "assoc_staff";
                    active: boolean; created_at: Instant };
type HoursInterval = { weekday: number; start_local: string; end_local: string }; // Proposed ISO weekday 1–7, HH:mm, start<end.
type Association = { id: UUID; name: string; registered_by: UUID; rna: string | null; siret: string | null;

type Capacity = { association_id: UUID; category: Category; unit: Unit; limit_quantity: Quantity;

type Indicator = { key: string; value?: string; probability?: number; level?: Level;

type IntakeChecks = { not_medicine: boolean | null; food_nonperishable_room_temperature: boolean | null;

type Distribution = { donation: Donation; movement: Movement; remaining_quantity: Quantity };

                       remaining_quantity: Quantity; unit: Unit; expiry: ExpiryRead };

                     basis_analysis: Analysis | null; category_mismatch: Mismatch | null; expiry: ExpiryRead };
type ExpirySummary = { reference_date: DateOnly | null; timezone: "Europe/Paris"; policy_version: string | null;
  bucket_mode: "cumulative" | "exclusive" | null; bucket_catalog: { key: string; label: string }[] | null;
  counts: Record<string, number> | null; total_items: number; unknown_dates: number };

                      name: string; address: string; latitude: number | null; longitude: number | null; description: string | null };
```

Indicator missing fields are omitted, preserving the optional shape of the AGENTS provider contract; NULL database columns do not become artificial probabilities. `Analysis.provenance` is sanitized component attribution, not raw provider logs. `ExpiryRead`, capacity/need/slot `computed` objects, mismatch and summaries are computed on reads and never accepted as writes or stored as expiry derivatives. Source facts remain available when policy is unresolved; an uncertain derived value is NULL with an explicit reason, not false/zero. High medicine warnings remain attributable to their original run after a category override; newer results do not erase history. A decision is always identified by human actor/time, separately from indicators.

## Write schemas

```ts
type ProfilePatch = { expected_revision: Revision; display_name: string | null };
type AssociationCreate = { name: string; rna?: string | null; siret?: string | null;
                           display_address?: string | null }; // At least one provided RNA/SIRET under DB-P01.
type AssociationPatch = { expected_revision: Revision; name?: string; display_address?: string | null;
                          opening_hours?: HoursInterval[] }; // Address is geocoded server-side.
type AssociationApproval = { expected_revision: Revision; approved: true }; // No rejection/reversal workflow inferred.
type NeedInput = { category: Category; attributes: Attributes; seasons: Season[] | null;
                   target_quantity: Quantity; unit: Unit; active?: boolean; source_text?: string | null };
type NeedPatch = { expected_revision: Revision } & Partial<NeedInput>;
type NeedParse = { text: string };
type NeedDraft = { draft: Partial<NeedInput>; source_text: string; warnings: { path: string; code: string }[] };
type CapacityPut = { expected_revision: Revision | null; unit: Unit; limit_quantity: Quantity }; // NULL=create only.
type SlotInput = { starts_at: Instant; ends_at: Instant; max_bookings: number; active?: boolean };
type SlotPatch = { expected_revision: Revision } & Partial<SlotInput>;
type DonationCreate = { donor_kind?: DonorKind; company_name?: string | null; category?: Category; attributes?: Attributes; quantity?: Quantity; unit?: Unit };
type DonationPatch = { expected_revision: Revision; donor_kind?: DonorKind; company_name?: string | null; category?: Category; attributes?: Attributes;
                       quantity?: Quantity; unit?: Unit; expiry?: ExpiryInput };
type AnalysisCreate = { expected_revision: Revision; photo_ids: UUID[] };
type LocationInput = { address: string }; // Proposed request-scoped location, privacy/radius policy AMB-009/016.
type MatchRequest = { location: LocationInput; limit?: number; cursor?: string };
type OfferCreate = { expected_revision: Revision; association_id: UUID; need_id: UUID; location: LocationInput };
type DecisionCreate = { expected_revision: Revision; decision: Decision; intake_checks: IntakeChecks };
type BookingCreate = { expected_revision: Revision; slot_id: UUID };
type QrResolve = { payload: string };
type ReceptionCreate = { expected_revision: Revision; payload: string; received_quantity: Quantity; confirm_received: true };
type DistributionCreate = { expected_revision: Revision; quantity: Quantity; unit: Unit };
```

PATCH merges only supplied top-level fields; supplied attributes replace the full category-validated object, and supplied expiry replaces the full source-fact object. Omitted top-level fields remain unchanged. Nullable fields may be cleared explicitly; never clear a field because the model could not read it. Store before/after facts and actor in `donation_edits` in the same correction transaction. Working fields become immutable after offering under DB-P02, except the audited staff quantity correction inside reception. Existing AI fields have **no** writable schema or update/delete endpoint.

Each donation contains one product type with one set of matching attributes and expiry facts. Multiple identical units are allowed. Donors must split mixed products, sizes, conditions, or expiry facts into separate donations before offering. Item quantities are positive integers.

DonationCreate defaults donor_kind to individual. A company donation requires a nonempty company_name snapshot. An individual donation requires company_name=NULL. DonationPatch validates the merged final values and permits changes only before offering. The authenticated subject always supplies donor_id server-side. A company name grants no ownership or association permissions.

Approval requires `not_medicine=true`, and `food_nonperishable_room_temperature=true` for food. Packaged food and para goods also require `packaged_unopened=true`. Opened packages are ineligible. The packaging assertion is not applicable to clothing, shoes, or furniture and remains NULL for those categories. Medicine-specific policy changes remain on standby; the existing exclusion still applies. Unknown or false required assertions cannot pass an approval; refusal may retain unknown assertions without pretending the AI refused. Warning thresholds, confirmation language and expired/DLC/DDM policy remain AMB-007. Input policy gaps return `policy_required`, not invented defaults. Correcting a medicine-like item's category does not remove the original concern or permit a confirmed medicine donation.

France uses `Europe/Paris` for local calendar dates, opening hours, and slot display. Instants remain timezone-aware and use UTC `Z` in responses. Association writes cannot override this zone. Printed PAO labels and months remain source evidence, but eligible donations have no opening date and no expiry calculated from opening. A PAO label alone does not supply a calendar expiry date.

Need criteria become immutable once an approval commitment or receipt references the need. Changes to `category`, `unit`, `attributes`, or `seasons` then return 409 `need_criteria_locked`. To change criteria, staff close the old need with `active=false` and create a new need. Existing donations and receipts retain their original need. Target changes still follow the existing commitment checks.

All examples and endpoints that depend on DB-P02–DB-P07 are conditional on agreeing those policies. Exact upload limits/formats, season rules, unit vocabulary, expiry boundaries, QR lifetime and signing configuration must be present before dependent operational actions can succeed. Read-time diagnostics can expose source facts with unresolved derived fields; this does not count as completing the required MVP expiry/FEFO behavior.

## Endpoint catalog

Paths are relative to `/api/v1`. GET bodies are empty; POST/PATCH/PUT bodies use the named schemas and command retry headers above. `Single<T>` and `Page<T>` are literal response envelopes. `api_requests` in the tables means `private.api_requests`. Success codes do not replace the common error contract. Every association/need/donation/slot/booking ID is validated and reauthorized; path IDs never confer membership.

Registration stores the authenticated applicant, never a caller-chosen admin role. Platform approval cannot silently provision an initial membership before AMB-002 is resolved; return a policy error if the agreed bootstrap prerequisites are absent. No membership invitation/role-assignment endpoint or association rejection workflow is invented. Coordinates are obtained/validated server-side when an address is saved; unavailable geocoding returns an error without replacing known coordinates with invented ones.

Association address is nullable in the proposed schema, while BookingDetail requires a usable drop-off address. AMB-010/016 must settle the booking prerequisite and whether changes to intake address or hours may affect existing appointments. Slot-time freezing alone does not cover these edits. Until agreed, this contract does not claim such configuration changes are safe for booked donations; no silent address snapshot or rescheduling workflow is added.

Upload validation checks actual file content/type, byte size and configured photo count server-side, before storage metadata is accepted and before any provider request. No arbitrary remote image URL is accepted. Photo bytes/digests remain immutable once referenced. Failure leaves no usable analysis input. Photo upload increments the donation revision; clients obtain the current version before analysis. The non-transactional Storage/metadata boundary and orphan policy are described in databases.md.

Photo.content_url is a FastAPI content-route reference, resolved against the configured API origin/path. The Next.js client fetches private bytes with the same bearer authorization and displays a temporary browser blob URL, releasing it when no longer needed. A plain image element or image optimizer does not automatically attach that Authorization header; do not make the bucket/content endpoint public to bypass this. Binary responses are streamed with validated MIME type and no-store. Neither photo DTOs nor list responses contain persisted base64 bytes. Current attributes are validated item facts/need criteria, as explained in [the database design](databases.md#what-attributes-means); metadata/provenance and original indicators remain separate.

Provider selection/model/provenance come only from server configuration. Optional Jev/hybrid modes remain behind `ANALYSIS_PROVIDER`; Jev never extracts dates/numbers and its image header is mandatory when enabled. Failures return errors with no successful analysis/decision row. Multiple result rows are preserved. Analysis completion only seeds working values for the first eligible basis at the captured revision; if a human edit or another analysis already established current facts, preserve them and return `working_facts_seeded=false`. Category mismatch is computed against the retained basis; no result is relabeled as a new category. Before offering, require a successful retained basis analysis with its validated photo evidence, not a fabricated empty result after failure. A mandatory reanalysis rule after category override is still AMB-004.

Matching uses code-generated reasons and code-computed Haversine distances. Request location is proposed to remain ephemeral; no donor address, distance or route is stored as a donation fact. Offer submission geocodes/rechecks the supplied location and current eligibility. Staff approval rechecks intake, approved association, active matching need, category/unit/season and sufficient capacity/demand under transaction locks; a human refusal does not require successful matching. If the eventual radius/privacy policy requires retaining origin coordinates for later revalidation, revise the protected source-fact schema before migrations (AMB-009/016). No default radius, weighted score, season vocabulary or stored location is silently adopted. Resolve the current official geocoding endpoint/adapter under AMB-021 before integration. Raw matching configuration/need text, donor coordinates and membership data are not returned to other donors.

The pre-implementation audit identified a basis-selection gap (AMB-004; [handoff AUD-004](handoff.md#blockers)): a first successful analysis can append evidence without seeding after a concurrent human edit, while offering requires a retained basis. Agree how a current basis is adopted/retried without overwriting human facts before freezing this contract. No implicit basis-selection endpoint is introduced here.

The sequence is offer submission, staff approval, donor slot selection, committed booking, then QR retrieval. Slot selection and QR are unavailable before approval. QR is unavailable until booking commits. Booking checks owner, explicit staff approval, target scope and remaining slot allocation in one transaction. Category capacity is already held under provisional DB-P04; booking does not double-reserve it. QR GET signs a minimal reference to booking ID/nonce/deadline using a separate server-only key. It contains no photos, diagnosis, provider result or donor address. No token lifetime or transport service is inferred. Client callers cannot supply QR expiry/nonce or receive a signing key. QR GET must reject an unconfigured policy, not emit an indefinitely valid token by accident.

QR resolve is read-only. Reception sends the QR again plus explicit confirmation, so a client-supplied booking ID cannot substitute for server validation. The FastAPI handler validates signature/deadline, then a server-only transaction command checks current nonce, scope, membership, status, expected revision and receipt uniqueness before writing. A direct authenticated RPC must not bypass QR verification. On an already-received request with a new key, return 200 current Reception only if it is demonstrably the same booking/event and received_quantity equals the recorded receipt quantity; otherwise return a state conflict. In all cases there is no second movement, need decrement or new receiver attribution. A repeated distribution with the same key replays its movement; a new action cannot exceed remaining stock.

A full reception records the actual received quantity once. Staff provide a positive integral received_quantity no greater than the booked donation quantity. If lower, the same transaction updates donations.quantity, appends a server-built before/after donation_edits record, inserts the receipt, changes status to received, increments the revision, and completes the retry record. The audit retains the original offered quantity and the actor. Stock and fulfilled need use the actual receipt quantity. Under provisional DB-P04, the old quantity hold disappears and actual stock replaces it in this transaction. There is no pending remainder or second receipt. Zero is rejected without a receipt or quantity edit. No-show, cancellation, release timers, reversals, and partial-distribution policy remain on standby or unresolved.

All counts, balances, expiry flags/buckets and FEFO ordering are deterministic read-time code/query results. Cumulative/exclusive bucket mode and exactly-90-day behavior are not hardcoded in the contract: the configured catalog supplies stable versioned keys/labels. Until policy is agreed, summaries may expose source/unknown diagnostics with NULL classification; a FEFO request or expiry filter that needs an unresolved rule returns 503 `policy_required`. The required MVP is not complete until the missing policy is resolved and tested. No endpoint persists derived expiry or treats an unreadable date as a refusal.

The booking sequence diagram summarizes a composed UI interaction. The REST contract commits the booking first and retrieves its QR separately. If QR rendering/retrieval fails after booking, preserve the committed appointment and retry authenticated retrieval; do not create another booking or imply the successful booking was rolled back. Signing policy must be configured before the dependent flow is usable.

## Filtering, ordering and pagination

`limit` defaults to 20, accepts 1–100; `cursor` is opaque and bound to endpoint, actor/scope, filters and sort context. No unbounded list or arbitrary SQL sort/filter expression is accepted. Most lists use `(created_at DESC,id DESC)` keyset pagination; stable tie-breaks are mandatory. Own memberships use `(created_at DESC,association_id DESC)` because that junction has no standalone id. Slots/arrivals use `(starts_at ASC,slot-or-booking ID ASC)`; redirect points use ID ascending. Photos within an item are bounded by configured upload count. Single-resource GETs and the bounded capacity collection do not paginate.

Query filters are scalar values: category/status/level/kind use their defined enums, active is `true|false`, and from/to are RFC 3339 instants with from < to. Arrival date is a valid DateOnly interpreted in the association's configured zone. No date/range is silently interpreted in the donor browser zone. The review collection defaults to offered and may filter any non-draft Status; unfiltered needs/slots include active and inactive configuration for authorized staff. Gallery category refers to working category, and indicator key/level filters refer to the retained basis analysis. Historical runs remain available from the analyses collection. Gallery pagination groups one donation before expanding its bounded photos; it does not duplicate items or inflate expiry counts through indicator joins.

Matches use a configured deterministic eligibility/order policy and a cursor containing all ranking tie fields, donation revision, location hash and candidate/policy context. The proposed nearest-first equivalent-candidate order is `(distance_km,association_id,need_id)` only after AMB-009 is agreed; do not silently introduce weights. FEFO cursors include source ordering fields, NULL/PAO placement policy, reference date/timezone and policy version. A changed derived-order context returns 409 `cursor_context_changed`, requesting a fresh first page. No distance or expiry rank is persisted to make pagination work.

Fetching page N of ordinary live lists is not a snapshot isolation guarantee; concurrent configuration/lifecycle changes may move records. Clients refresh after a mutation and identify items by stable ID. `has_more`/next_cursor are derived by fetching one extra authorized row/result; do not expose global totals from unscoped queries. Page joins apply authorization before counting, not after fetching a foreign tenant's data. Index definitions supporting these access paths are in databases.md.

## Route and framework consistency

The signed-in account uses `/account/profile` and `/account/memberships`; there is no `/me` alias or caller-selected account ID. The GET/PATCH profile schemas now describe the same resource rather than returning an aggregate on GET and a profile on PATCH. Membership reads do not imply invitation/role-assignment endpoints. The catalog contains 42 business operations; FastAPI's optional OpenAPI/docs tooling is not counted as a product operation.

All path IDs are UUIDs checked against parent scope; child IDs do not override their association/donation parent. Use plural names for collections and explicit bounded action/subresource names where there is no independent table (`matches`, `offers`, `decision`, `qr/resolve`, `reception`). An offers path updates the existing donation aggregate; it does not invent an offers table. Read-like POST operations do not persist state. Preserve the catalog's HTTP status, retry and permission semantics across routers.

Register static paths such as `/needs/parse` before compatible parameter routes in FastAPI, and check the final OpenAPI path/method set for accidental shadowing or duplicate operations. Normalize FastAPI validation/HTTP/domain exceptions into the common error envelope; its default validation response is not automatically this contract. Query validation, response serialization, multipart limits, CORS preflight and no-store headers need explicit integration checks. These are implementation requirements, not configured middleware today.

## Error contract

Application-generated errors use ErrorResponse with `application/json`. A framework/hosting rejection before a FastAPI handler runs (for example unsupported method or a platform body limit) can have an empty/non-JSON body; clients must handle the HTTP status without displaying a raw upstream page. Unsupported methods retain the appropriate Allow header. Binary photo success responses do not use a JSON envelope.

| HTTP | Representative codes | Meaning / retry behavior |
|---|---|---|
| 400 | `invalid_json`, `missing_idempotency_key`, `invalid_cursor` | Malformed protocol input; fix request. |
| 401 | `authentication_required`, `invalid_session` | No valid authenticated subject; do not turn Auth service outage into a false login success. |
| 403 | `permission_denied` | Known capability unavailable, e.g. non-platform caller to admin endpoint. |
| 404 | `not_found` | Missing or unreadable resource/foreign scope; no existence leak. |
| 405 | `method_not_allowed` | Only the documented methods are supported. |
| 409 | `stale_revision`, `capacity_full`, `need_unavailable`, `slot_full`, `state_conflict`, `idempotency_conflict`, `request_in_progress`, `cursor_context_changed`, `need_criteria_locked` | No partial business write; refresh/fix, or retry same key only when retryable. |
| 413 / 415 | `file_too_large` / `unsupported_media_type` | Server rejects upload before a provider call. |
| 422 | `validation_failed`, `invalid_qr`, `intake_restriction` | Valid JSON but invalid values, signature/deadline or confirmed excluded item. A restriction is code-enforced product scope, not an AI refusal. |
| 429 | `rate_limited` | Configured protection limit; respect Retry-After when supplied; no rate value is invented here. |
| 502 / 503 / 504 | `analysis_failed`, `geocoding_failed`, `service_unavailable`, `policy_required`, `upstream_timeout` | No fabricated result/coordinate/decision. `policy_required` includes AMB IDs and is not transiently retryable until configuration is resolved. |
| 500 | `internal_error` | Safe message + request ID only; never raw SQL, credentials or provider payloads. |

Constraint/lock/serialization failures are translated to stable domain codes. Retryable deadlock/serialization/temporary service cases may use bounded internal retries with the same retry key; exhausted temporary contention returns 503 `service_unavailable`. Never retry a failed committed action with a new key just to bypass a conflict.

## Delivery and verification boundaries

Accepted-rule checks for the future implementation:

- A need for size-M jackets with a receipt cannot change to size L. The command returns 409 `need_criteria_locked` without changing fulfillment. Staff can close that need and create a size-L need.
- A concurrent need edit and approval use the same locks. Either the edit commits first and approval rechecks the new criteria, or approval commits first and the criteria edit fails.
- An opened packaged food or para item cannot pass approval. A clothing donation does not require a packaging assertion. Original PAO extraction remains readable, and `opened_on` is not an accepted input.
- A company donation requires a company_name and remains owned by the authenticated donor. Neither donor kind permits chilled or opened food. An individual donation cannot retain a company name.
- Three identical cans with one expiry date can share a donation. Cans with different expiry dates require separate donations.
- Slot selection fails before staff approval. QR retrieval fails before booking commits. A last-slot race produces one booking and one slot_full conflict.
- For a booked quantity of 3, reception of 2 commits quantity=2, an audit of 3 to 2, one receipt of 2, and received status together. No remainder stays pending. A retry creates no second audit or receipt. A foreign association, stale revision, zero quantity, or quantity of 4 commits none of those changes.
- A read around midnight uses the date in `Europe/Paris`, including daylight-saving changes. Responses still serialize instants in UTC.

The same database commands enforce the [atomic transaction rules](databases.md#atomic-transactions-and-concurrency); FastAPI boundary guards alone are insufficient if direct table/RPC access bypasses them. Contracts must be checked for two-donor/two-association isolation, forbidden fields, immutable evidence after category edits, strict provider schemas, stale versions, retry-key collisions, last-capacity and last-slot races, duplicate/foreign QR, excessive stock distribution and the configured expiry boundaries. Use requirement NFR-009's application commands/photo fixtures once the app exists.

No transport, vehicle routing, pickups, email, messaging, role invitations, cancellation, re-offering or advanced impact API is added to the MVP. Optional provider comparison/reporting endpoints can be designed after their cut-order and measurement policies are agreed (FR-026–FR-032). The proposed 40-hour baseline remains the vertical slice in features.md; this document specifies its contract without implementing it.
