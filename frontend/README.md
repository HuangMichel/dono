# Dono frontend demo

Next.js App Router, TypeScript, Tailwind and shared shadcn-style controls. Data and actions are browser-local simulations based on [the API contract](../docs/api.md), with the explicitly requested [frontend demo extensions](../docs/requirements.md#current-frontend-decisions--2026-10-25). No backend or API endpoints are implemented.

## Run

Use pnpm 11.0.9 and a compatible Node.js release. Checks in this workspace used Node.js 25.9.0.

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Open `http://localhost:3000`. No environment variables, passwords or service accounts are needed. Webpack is explicit in the development and build scripts. Dependencies and the lockfile were prepared from the existing local package cache; three transitive pins in `pnpm-workspace.yaml` keep that installation reproducible.

## Design and components

Layouts follow the selected [mockups](../docs/design/README.md). [DESIGN.md](../DESIGN.md) controls semantic colors, typography, widths and accessibility. Public/donor pages and association/platform pages share buttons, fields, cards, chips, headings and icons from `components/ui`. Button variants use Radix Slot and class-variance-authority; `components.json` records the shadcn configuration.

The frontend includes item photography, analysis, correction and offer states; split public/auth screens; the staff review queue; the monthly slot calendar; reception; stock; and platform approval. Browser-local reception refusal and unmatched-offer posting are explicit demo extensions. Other API-unsupported actions remain unavailable. Mockup statistics use sample data or show an explicit unavailable state.

Shared `DataTable` controls provide search, column sorting and single-row selection for donations, needs, stock and platform approvals. Tables show 10 rows per page by default. Search and sorting apply to all rows before pagination and return to page 1. A selected row remains selected across pages. If rows disappear, the current page stays within the available range. Desktop and mobile show the same page. Click a row background or press Enter/Space on a focused row to toggle selection. Selecting another row replaces the previous selection. Detail buttons and other row actions remain independent. A stronger green background marks the selected row; its checkmark aligns with the first text line on desktop and mobile. Expanded evidence wraps within the table width. The search field has a leading icon and sits above the bordered table. My donations places search beside the status filters on desktop and wraps the controls on narrow screens. Other tables keep a full-width search field. The shared `Calendar` starts on today in Europe/Paris, supports keyboard navigation and has a Today control. Donor booking hides past, closed and full slots; the Drop-off location dropdown contains the approved association's address. The console places the profile at the top left and provides a navigation toggle. Registration and item photography use the same `Stepper`. Their Back and Continue actions use a separate shared footer below the step content.

Cards with actions use the shared `CardActions` footer. Actions stay at the bottom, including gallery cards with different text lengths.

The console navigation shows shared icons and count chips for waiting reviews, expected drop-offs, remaining stock items, active needs and pending platform approvals. Collapsing it keeps a narrow icon rail with accessible labels. Mobile navigation retains full labels. Reception cards have compact More details/Hide details controls; hiding a card preserves its entered quantity. Selecting a Needs row opens its editor directly. Deselecting, cancelling or saving clears that selection.

On Needs, Describe a need supports browser voice input and a typed description. Use sample fills the supported fictional description. Prepare sample draft loads editable fields without saving; Confirm and publish need is the staff action that creates the need. Arbitrary descriptions do not produce simulated AI results. The original sample transcript is retained in `source_text`. No model or application API is called. Browser speech recognition has limited availability and may process audio through the browser's speech service; see [SpeechRecognition documentation](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition). The microphone starts only after Record description is pressed, and recording ends on stop, editing, errors or leaving the page.

The photograph step uses shared `FileUpload` controls for multiple item views and a separate optional label. Batch and successive selections append to a gallery with individual replacement, removal and main-photo selection. The demo allows six item photos plus one label, with JPEG/PNG/WebP and signature validation and a 5 MB limit per file. Invalid files have filename-specific errors; stale reads cannot restore removed or replaced previews. The selected main photo and gallery remain through review and Back to photos. The three equal step columns, upload area and action button share one width. Thumbnail filenames and action rows align; mobile upload cards stack. Its icon-only Back arrow returns to `/donate` without deleting the saved draft. The donation start page has a Back arrow to `/`. Each page shows one 44 px Back control, above the heading on desktop and in the header on mobile. These links work on direct entry without relying on browser history. Donor and registration step buttons show left arrows before backward-action labels and right arrows after forward-action labels. Review step buttons stack on mobile. Local image previews remain temporary. The correction dialog is centred with internal scrolling when needed. Escape and Close discard unsaved corrections; Save keeps them.

The sign-in page links to `/signup` through Create a donor account. Both pages share `AuthLayout`. Credential fields remain disabled; Continue as a demo donor opens the existing fictional donor flow without creating an account or collecting a password.

## Association dashboard

The dashboard has four linked action cards: offers waiting for review, expected drop-offs today, active needs still uncovered, and categories above 85% capacity. Capacity includes stock plus approved/booked reservations. A zero limit is paused. Need progress keeps Received, Reserved and Still needed separate. A reservation does not count as received.

Stock, needs, capacity, matching and the dashboard share association-scoped balance calculations. Movement IDs are deduplicated after association and donation checks. Current stock and need fulfillment use recorded inventory movements. Weekly received and given-out quantities use their event dates, including partial distributions. Invalid or future times are excluded from weekly activity. Quantity calculations retain the contract's three-decimal precision. The reporting week starts Monday at 00:00 in Europe/Paris. Refusals at reception show recorded staff reasons and a count, without an unsupported refusal rate. Unknown offer times do not use draft creation times. No expiry, urgency, missed-appointment or environmental KPI is inferred.

Future API integration can load the headline KPIs from association reviews, arrivals, active needs and capacity. Collection counts require all cursor pages, and ordinary pagination does not guarantee an atomic snapshot. The proposed API has no movement-history read for weekly activity and no reception-refusal contract. Inventory balances cannot reconstruct those histories. These sections currently use browser-local demo records; no API connection or backend endpoint is implemented.

## Explore the demo

1. Open `/login` and choose the donor persona.
2. Create a draft at `/donate`. Open Sample controls to choose a scenario. Photograph an item, add a local image preview or use the illustration, then run sample analysis. The fixed sample description creates two separate drafts; arbitrary text is not parsed.
3. Correct working details and send an offer. Original indicators remain separate. Medicine and chilled-food scenarios retain their warnings.
4. Switch to the association persona at `/login`. Review the offer at `/association/review` and make an explicit staff decision.
5. Return to the donor persona. Open `/donations`, book an approved item and view its demo pass. The QR failure control preserves the booking.
6. Switch to the association persona. Paste the displayed `DEMO-ONLY:` reference at `/association/reception`. Confirm a positive quantity no greater than the offered quantity, or refuse the entire unreceived donation with a reason and explicit staff confirmation.
7. Distribute received stock at `/association/inventory`. Remaining quantities update from the local movements.

Refusal at reception creates no receipt or stock movement. It preserves the offered quantity, original approval and booking history, releases provisional need/capacity holds and slot occupancy, and prevents later receipt or rebooking. Donors see the staff reason. Direct booking pages show closed history without a QR. The browser-local `reception_refusals` records survive reload; older saved state initializes this collection without a reset. No refusal endpoint or public DTO was added.

When no association currently matches, Post offer makes the analyzed item available in the association's Posted offers view. The donor sees Posted in My donations and can withdraw the post to edit the preserved draft. The listing contains item facts, sample indicators and a labelled sample illustration, without private donor details. Uploaded photo previews remain temporary and do not appear in the persisted listing. Posting does not assign a recipient or create an approval, reservation, appointment or stock movement. Medicine and chilled-food warnings still block posting. Claiming remains unavailable. This is a browser-local extension with no publication API.

Open tabs on the same browser origin synchronize saved demo data. Each tab keeps its selected role, so a donor can post or withdraw an item while an association has Posted offers open. Actions read the latest saved data before applying changes, which prevents an older tab from overwriting a newer post. If local changes could not be saved and another tab changes the browser copy, the warning explains that Retry saving replaces that copy; no automatic merge occurs. This remains a local demo: different browsers, devices and origins do not share data, and truly simultaneous writes are not atomic.

Capacity cards and the dashboard share a percentage meter computed from stock plus reservations against the limit. Green covers values through 60%, orange covers values above 60% through 85%, and red covers values above 85%. A zero limit remains a neutral Paused state. Every meter shows the 60% and 85% threshold markers. The marker labels, colors and near-capacity KPI use the same threshold rules.

The console also provides needs, capacity, slot and image views. Duplicate Category dropdowns under More filters and FEFO/distribute-first controls and panels are removed. Main category controls, source dates, indicator filters and ordinary stock distribution remain. `/company` records a company name on a donor-owned donation. `/register-association` has three steps: Identity, Drop-off address and Review. Identity requires a name and an RNA number, a SIRET number, or both. Missing required fields show a red border, a light red background and linked error text after interaction or a failed submission. Optional and disabled fields remain exempt. A supplied SIRET is normalized and checked for 14 digits, the SIREN and SIRET checksums, and the La Poste exception, following [INSEE FrLab validation rules](https://github.com/InseeFrLab/validinsee#validité-de-numéros-siren-ou-siret). This is a local input check; no registry lookup or automatic approval occurs. The drop-off address is optional. Submission creates a pending registration; the platform persona reviews it at `/admin`. Categories, capacity and appointment slots are configured after activation. This flow follows `AssociationCreate`; it does not use the mockup's provisional Categories step.

Nearby needs shows up to 10 sample needs per page. The current five samples fit on one page. Location is optional. An empty or whitespace-only search shows all sample needs in the selected category. A nonempty location keeps the sample listings and explains that distance filtering is unavailable. Location text does not call a geocoder. The Location field, Search button and category filters keep their alignment when helper text changes. Changing the category or submitting a search returns to page 1 and clears stale item selection.

User-facing terms distinguish staff decisions, item indicators and demo limitations. Posted offers does not imply nearby matching. Reception uses Look up a drop-off and Demo booking reference. Donor labels expand Period after opening and use readable indicator names. Status labels include Waiting for review and Given out. Stored enum values and API fields stay unchanged.

Platform approvals use one selected association for the row highlight, detail panel and approval action. Clearing selection or changing the status filter removes the approval target. Visitors can choose the donor demo persona on the registration Review step without leaving the page or losing their entries. Company drafts reject a product description containing only spaces before opening the photo step. Shared fields preserve explicit accessible names supplied by their callers.

Local demo controls reset browser data. Reset once to see the expanded fixtures if this browser already contains an older demo. State uses localStorage key `dono-demo-v1`. If saving fails, the demo keeps current changes in memory and shows a browser storage warning with Retry saving. A later successful write or retry saves the latest complete session without repeating its actions. If earlier browser data cannot be read, ordinary actions leave that copy untouched. The warning explains that explicitly retrying replaces it with the current session. Registration and offer confirmations identify session-only changes. Photos selected from disk are temporary previews and are not uploaded or stored there.

## Boundaries

- Personas are simulations, not authentication or access controls. Never enter private data into this demo.
- Analyses use fixed fictional indicators. They do not inspect uploaded images or call a model.
- Matching checks local needs and capacity. Distance is an explicitly labelled example; location text does not call a geocoder.
- The QR contains an unsigned local reference. Reception lookup simulates the flow; it does not verify a signature or use a camera.
- Source dates and read-time day counts are visible. FEFO controls are removed at the user's request. Expiry buckets and unresolved intake policies are not invented.
- Public needs are separate illustrative listings. Public claiming, messaging, transport, disposal, cancellation and unsupported API actions are unavailable.
- The demo has one donor and one active association. Browser state is not a database transaction, durable idempotency ledger or multi-user authorization system.
- DM Sans loads from Google Fonts at runtime, with a system fallback. Builds do not download fonts.
